# CLAUDE.md

Guidance for working on s3rp. See README.md for user-facing documentation.

## What this is

s3rp is a PoC toward a multi-tenant S3-compatible object storage service: an S3 API reverse proxy that authenticates clients by SigV4 with tenant/user access keys and re-executes operations via aws-sdk-go-v2 against per-bucket backends (Ceph RGW, versitygw, Amazon S3, ...).

It deliberately reconstructs operations through the SDK instead of transparently forwarding requests: a multi-tenant service needs to understand every operation anyway (authorization, metering, quota), must present a uniform API surface regardless of backend, and must hide backend bucket names in responses.

## Architecture

- `s3gw/` **is the proxy**: signature verification, authorization, the operations and the routing that reaches them. It depends only on the leaf packages and a `store.Store`, never on the root package.
- Root `package s3rp` is the service assembled from a config — the YAML schema and its store, the HTTP server, the CLI — and is deliberately small (~500 lines). `S3RP` embeds `*s3gw.Gateway`, so the assembled service exposes the gateway's API. `cmd/s3rp/` is a thin main.
- `store/` is the read-only contract for tenant/user/bucket/backend definitions (`store.Store` interface plus domain types `Key`, `Bucket`, `BucketEntry`, `Backend`, `Password`, `CORSRule`). `Store.ListBuckets` returns light `BucketEntry` values (name + created-at) so a listing does not materialize full definitions; `Bucket.CreatedAt` carries the same date on the full definition (zero = unknown, ListBuckets then reports the Unix epoch). The bundled implementation is the YAML config (`configStore` in the root package); a real service implements the interface against its own storage. A sqlite implementation (`store/rdb` + `db/` + `cmd/s3rp-admin`) existed and was deliberately removed: it dragged a sqlite dependency into the module and a definition store is exactly the part a service must design for itself — do not reintroduce one. Bucket policies and CORS rules are carried on `store.Bucket` (policy as raw JSON text + parsed form). Anything a store loads besides the definitions travels on `Bucket.Metadata`/`Key.Metadata` (opaque to the gateway; see Hooks).
- `policy/` parses and evaluates AWS-style policy JSON. Leaf package, also usable by an external store.
- **Reusable leaf packages.** A production service built on this PoC is expected to reuse whole packages rather than fork the proxy, so keep these free of proxy-specific types: `policy/` (stdlib only), `checksum/` (stdlib only — the S3 checksum algorithms and their headers; it takes the checksum type as a plain `string` specifically to avoid an aws-sdk dependency, so callers convert `types.ChecksumType`), `s3err/` (the S3 XML error response and the aws-sdk error mapping; depends on smithy because mapping SDK errors is the point), `sigv4/` (server-side SigV4 verification and aws-chunked decoding — depends only on `checksum/` and `s3err/`), `cors/` (rule matching and the preflight/actual response headers; `store.Bucket.CORS` is `[]*cors.Rule` directly), and `store/` (the definition contract a real service implements against). `s3xml/` holds the S3 API's XML request and response bodies plus `s3xml.Write`; the API speaks XML, so any implementation needs them and they carry no proxy logic. The operation layer and routing live in `s3gw/`.
- Request flow: verify signature (auth.go) → resolve bucket via Store → evaluate bucket policy (bucketpolicy.go) → dispatch (handler.go) → operation (proxy.go, multipart.go, copy.go, tagging.go, versioning.go, acl.go, cors.go).
- Backend clients are built lazily and cached by backend identity (endpoint/region/credentials/path-style); clients are bucket-agnostic. The cache is an LRU (hashicorp/golang-lru, default 128 entries, `Gateway.SetClientCacheSize`) because with an external store backends grow with tenants and each client owns a connection pool; an evicted client is just rebuilt on its next request. Note `SetBackend` (test stubs) pre-warms this same cache, so a stub can in principle be evicted and silently fall back to a real client — irrelevant at default capacity, but don't shrink the cache in tests that use stubs. The cache key must keep covering exactly the fields `newBackendClient` reads — the bucket is deliberately excluded, everything else must be present or differently-configured backends would silently share a client.
- Optional backend fields are resolved by `store.Backend.SetDefaults(bucketName)`, which **every** Store implementation must call (the config store applies it at load time; an external store after building each `Backend`). Stored definitions may legitimately omit `use_path_style`/`region`/`bucket` — they are `omitempty` — and the client builder used to dereference `*UsePathStyle` unconditionally, so a backend built without `SetDefaults` panicked the request path.

## Domain model decisions (do not regress these)

- A tenant owns buckets and users. A **user** (`[a-z][a-z0-9_-]+`, unique per tenant) is the rotation-stable identity; access keys rotate under it. **Never use access key ids as policy principals.**
- Bucket names and access key ids are globally unique across tenants (path-style URLs carry no tenant discriminator; `Store.GetBucketByName` relies on this for unauthenticated CORS preflights).
- Bucket policy: AWS-style JSON text; principals are plain user names under the `"S3RP"` key, `"*"` = all users, `NotPrincipal` = everyone-except; resources are plain `bucket/prefix*` (no ARNs anywhere — explicit owner preference). Semantics: tenant users have full access as the baseline; explicit Deny restricts. Allow is inert until anonymous / cross-tenant access exist. The principal key and a resource ARN prefix are surface syntax only, configurable via `policy.Dialect` (normalized in the single parse pass; `policy.Parse` = zero Dialect); the internal form, the evaluator and the caps are dialect-independent and must stay that way — never make evaluation itself configurable. `store.Bucket.PolicyText` is what GetBucketPolicy returns and is deliberately not required to be the parse input, so a dialect store keeps the tenant's original text there.
- Policies are tenant-authored and evaluated on every request (per object for DeleteObjects), so they are untrusted input with structural caps enforced at parse/validate time (`policy.Max*`: 20 KB total document, 20 statements, 30 actions, 10 resources, 128-byte patterns, 100 principal users; the byte cap is checked before unmarshal so an oversized document is rejected without being parsed into memory). The worst-case cost is dominated by the total resource-pattern count (`MaxStatements*MaxResourcesPerStatement`) — each adversarial resource pattern can force a full scan of the object key — not by pattern length or the byte cap; action matching is against a short string and stays cheap, so `MaxActionsPerStatement` is generous. — the glob matcher is O(n·m) (no ReDoS), but unbounded size would still let one authorization do unbounded work. Perf: patterns are compiled to `[]rune` once (lazily via `sync.Once` on first `Evaluate`/`Allows`, so `Policy`/`UserPolicy` carry a lock and must be passed by pointer), and the matched value is converted to runes once per call rather than per pattern; together this keeps a maxed-out policy's evaluation in the low microseconds. DeleteObjects authorizes per object but resolves the resource-independent parts once via `app.perObjectAuthorizer` / `policy.DenyEvaluatorFor` (user policy + the bucket policy's matching Deny statements), so only the resource is tested per key; when no Deny matches the user and action (the common case), `perObjectAuthorizer.allowsEverything` (backed by `DenyEvaluator.AlwaysAllows`) skips the per-key check and its resource-string construction entirely — de-amplifying the ×1000 to O(1). Only a policy with resource-discriminating Deny rules for the action pays per key, bounded by the resource-count cap.

  Caveat on where the precompilation pays off: `configStore` builds each `Policy`/`UserPolicy` once at startup, so patterns are compiled once for the process. An external store that re-parses the policy text per request also re-compiles per request, so there the win is only within a single request's evaluations — a store cache should hold the parsed `*Policy`/`*UserPolicy` (documented in the README). Keep this in mind when reading the benchmarks — they measure a warm, long-lived policy.
- The user-policy byte cap (`MaxPolicyBytes`) applies to the **serialized** form, so it lives in `policy.MarshalUserPolicy` (used by config validation), not in `ValidateUserPolicy`, which stays allocation-free on the per-request path — do not move the cap back into it. An external store should check the length of the raw stored policy text directly.
- User policy (`policy.UserPolicy`, carried on `store.Key`): action-only identity policy attached to a **user**, no resource/principal. Evaluation is IAM-style and separate from the bucket-policy baseline: no policy = allow `s3:*`; with a policy only `Allow`-matched actions pass (unmatched = implicit deny), `Deny` wins. `app.authorize` checks it **before** the bucket policy — a request must pass both layers (user policy allows AND bucket policy does not Deny), so it lives at the same single chokepoint and covers every operation.
- ACLs mimic ACL-disabled buckets (AWS default since 2023): GET returns a fixed tenant-FULL_CONTROL stub, writes get `AccessControlListNotSupported`. Do not proxy ACLs to backends.
- SSE (s3gw/sse.go): SSE-S3/SSE-KMS pass through — the backend encrypts, the KMS key id is an opaque name its KMS resolves (e.g. RGW → Vault-compatible service), and the result headers are forwarded back. The requested mode and key id are exposed as `Op.SSE`/`Op.SSEKMSKeyID` because key-ownership (and per-backend capability) authorization can only happen at the gateway: the backend's KMS request carries no tenant identity, and a backend without SSE may silently ignore the request instead of refusing. **SSE-C is refused loudly** (`NotImplemented`, checked once in `dispatch` for every operation) — silently dropping the customer key headers would store the object unprotected while the client believes otherwise; never regress this to a silent drop. Integration: RGW needs `rgw_crypt_require_ssl=false` over plain http, and compose configures RGW's built-in `testing` KMS backend (static `testkey-1`) so SSE-KMS is testable without a KMS; the subtest skips on backends that don't encrypt (versitygw).
- CORS is handled by the proxy (not the backend): preflight `OPTIONS` is unauthenticated and handled before signature verification. Required for browser-direct presigned uploads. Rule evaluation lives in `cors/`; the proxy only resolves the bucket and turns a refusal into `AccessForbidden`. `cors.AllowPreflight` writes nothing when it refuses, so the caller still owns the response. Wildcards apply to both `allowed_origins` and `allowed_headers`, matching AWS.
- Bucket lifecycle (TTL) is deliberately not proxied: enforcement is the backend LC daemon's job, rules are written to the backend bucket by the control plane (same split as bucket policy / CORS writes). Do not add a PutBucketLifecycleConfiguration pass-through without solving the single-config collision — a bucket holds one lifecycle configuration, so a tenant PUT would replace the operator's baseline rules (e.g. stale-MPU abort); it would need a merge layer. A read-only GET (from a store record, like GetBucketPolicy serves PolicyText) is the acceptable first step if tenants need visibility.
- Object Lock is passed through to the backend (WORM enforcement is the backend's job). Bucket must be created with Object Lock enabled on the backend (s3rp does not proxy CreateBucket). Backend behavior differs — Ceph RGW/S3 honor governance bypass, versitygw does not — so the integration ObjectLock bypass-delete is best-effort, not asserted.
- CopyObject / UploadPartCopy work only between buckets on the same backend; the source resolves within the requester's tenant, making cross-tenant copies impossible by construction.
- Two tenants must not map front buckets to the same physical backend bucket (endpoint + backend bucket name); config validation rejects it, since sharing a physical bucket would break tenant isolation (within one tenant it is allowed).
- Responses must expose the **front** bucket name (ListObjectsV2 `Name`, multipart results, error `Resource`), never the backend bucket rename. The same goes for the backend's region: GetBucketLocation and HeadBucket's `x-amz-bucket-region` report the gateway's own region (`SetRegion`, us-east-1 when unset) — the backend region is backend identity, and reporting it would also make a region-honoring client re-sign with a region a pinned verifier refuses. Likewise every `Owner`/`Initiator` a response exposes (object/version/multipart listings via `tenantOwner`, the ACL stub, ListBuckets) is the tenant, never the backend account the proxy authenticates with.

## SigV4 verification (`sigv4/`) — the trickiest part

Verification re-signs a clone of the request with the SDK's own `v4.Signer` and compares signatures (constant-time). Non-obvious details:

- `SignerOptions.DisableURIPathEscaping = true` (S3 mode) or keys containing `/` break.
- The signing region is parsed from the client's credential scope, not configured; by default any region verifies, which is sound (the signature commits to the region) and right for a front endpoint with no inherent region. `Verifier.SetRegion` / `Gateway.SetRegion` optionally pin it for multi-region deployments — the value is fail-fast on misdirected clients (AWS's exact `AuthorizationHeaderMalformed` / `AuthorizationQueryParametersError` wording, naming the expected region) and restoring the blast-radius scoping of SigV4's derived keys, not signature integrity.
- The signer includes `content-length` in canonical headers based on `Request.ContentLength`, not the header map — the clone sets the field when the header was signed.
- The clone preserves the raw request escaping via `url.ParseRequestURI(r.RequestURI)`.
- **One signer per access key** (`signer.go`). `v4.Signer`'s internal derived-key cache holds a *single* entry keyed by (service, region) and validates it against the request's access key id — right for an SDK client with one credential, wrong for a proxy that signs with a different key almost every request: every request misses, re-derives the signing key, and takes that cache's **write lock**, so verification serializes process-wide (measured: with 16 keys the parallel case ran *slower* than serial, 16.4µs vs 13.8µs). `signerCache` is a direct-mapped table (default `defaultSignerSlots` = 512, resizable via `Verifier.SetSignerCacheSize` / `Gateway.SetSignerCacheSize`; collisions just replace the occupant) so memory stays bounded — access keys are per user and can grow without limit, unlike backends. It is deliberately **not** an LRU: golang-lru takes an exclusive lock even on `Get`, which would reintroduce exactly this serialization. Guarded by `BenchmarkVerifyKeyDiversity`. Cache statistics (`Verifier.SignerCacheStats` / `Gateway.SignerCacheStats`, and `ClientCacheStats` for the client LRU) are atomic counters precisely so the lock-free shape survives — never add a lock for bookkeeping here. Note that bench's manykeys allocs jitter run-to-run: 32 keys land in one of 512 slots by maphash seed luck, a pair collides in roughly six runs out of ten, and a collided pair rebuilds signers on every alternation — pre-existing behavior, now visible as `Evictions` in the stats. The bench lives in `s3gw` (not the root package) on purpose: measured through the assembled app, the root observer's synchronous slog formatting and its writer mutex dominated the parallel numbers and masked the very scaling the bench guards (parallel dropped from ~11µs to ~5.6µs when the observer left the loop).
- Temporary credentials: `SecretLookup` returns a `Credential{SecretAccessKey, SessionToken}`; a set token must be presented exactly (header `X-Amz-Security-Token`, presigned query, or POST form field — constant-time compare, `InvalidToken` otherwise), and a token on a long-lived key is refused rather than dropped (same principle as SSE-C). The token rides into `aws.Credentials` for the re-signing, so the SDK signer includes it the same way the client's did. Expiry and issuance are entirely the store/control plane's: an expired key is a `GetKey` not-found, and the gateway has no notion of it.
- The package takes the secret through a `SecretLookup` callback and returns only signature facts (`sigv4.Verified`); the tenant/user/policy behind the key are this service's domain and are attached by `verifiedRequest` in auth.go, which **embeds** `*sigv4.Verified` so the operation layer keeps reading `vr.PayloadHash` unqualified. The proxy's lookup closure captures the `store.Key` it finds, so the key is fetched once, not twice.
- Presigned URLs verify the same way via `PresignHTTP`; auth query params are stripped first (the signer re-adds them). S3's presigner disables header hoisting (signed `x-amz-meta-*` must be sent by the uploader) and strips Content-Type from presigned PUTs.
- Browser-based POST uploads (postpolicy.go) are the third SigV4 mechanism: the signature is a single HMAC over the base64 policy string with the scope-derived key (`deriveSigningKey`, shared with chunked.go), so there is no canonical request. The signature is verified **before** the policy JSON is parsed — an unsigned document is never unmarshaled — and the document is size-capped (20 KB, AWS's limit) with a condition-count cap. Evaluation is two-way: every condition must hold AND every submitted field must be covered by a condition (exempt: `policy`, `x-amz-signature`; the handler strips `x-ignore-*` and adds `bucket` as a pseudo-field so the policy binds the target bucket). The AWS docs' worked example is the known-answer fixture, like the chunked vectors. The routing branch is in `handleRequest` before header/query verification (multipart/form-data POST to a bucket path); the handler (s3gw/postobject.go) reads form fields up to the `file` part (fields after it are ignored, as on AWS), substitutes `${filename}` into the key *before* conditions are evaluated, streams the file to PutObject bounded by the policy's content-length-range maximum, and deletes+refuses an upload that ends below the minimum (only knowable at EOF). Unknown form fields are 501, mirroring unknown query subresources.
- aws-chunked bodies (`STREAMING-AWS4-HMAC-SHA256-PAYLOAD` and trailer variants) are mandatory to decode — the aws CLI uses them for every upload over http. chunked.go verifies the per-chunk HMAC chain seeded by the request signature; AWS docs known-answer vectors are the test fixtures. Each chunk is verified the moment its data completes (not on the following read), so integrity does not depend on the consumer reading to EOF. That alone is not enough, and a security review found the gap: consumers stop at `x-amz-decoded-content-length` (the SDK bounds the body by Content-Length), so a chunk claiming more than the declared decoded length still allows would have its leading bytes delivered and its signature never reached. `NewChunkedReader` therefore takes the decoded length and refuses such a chunk **at its header**, before delivering anything — do not drop that argument. The same review: a declared `x-amz-trailer` checksum that never arrives is now `BadDigest` (silently accepting it would claim an integrity check the client never proved), framing lines are bounded (`maxChunkLineLen`, the server sets no body read timeout), and client-controlled values quoted into errors are truncated since the cause reaches the observer's log.
- Payload integrity: the SigV4 signature commits to the `x-amz-content-sha256` header value, not the bytes. Since the backend is sent the body as `UNSIGNED-PAYLOAD`, the proxy verifies the body against a concrete signed hash itself (proxy.go `payloadVerifier`, `XAmzContentSHA256Mismatch` on mismatch); `UNSIGNED-PAYLOAD` requests have nothing to verify. A body-read `*S3Error` surfaces to the client because `fromSDKError` unwraps it via `errors.As`.

## Checksums (`checksum/`)

`x-amz-checksum-*` flows end-to-end: precomputed headers pass through; trailing checksums in aws-chunked bodies are verified by the proxy (chunked.go, `BadDigest` on mismatch) and the algorithm is forwarded as `ChecksumAlgorithm` so the backend SDK recomputes and stores it — an explicit `ChecksumAlgorithm` forces calculation even under `RequestChecksumCalculationWhenRequired`. Downloads forward `x-amz-checksum-mode` and return the backend's checksum headers. Whether checksums exist depends on the backend (versitygw yes; the ceph/demo RGW build does not store them — the integration Checksum subtest skips there). CRC64NVME uses `crc64.MakeTable(0x9A6C9329AC4BC9B5)`; values are base64 of the big-endian sum.

## Backend client construction (backend.go) — real failure modes

Two settings are load-bearing for non-AWS backends; removing either breaks PutObject:

- `v4.SwapComputePayloadSHA256ForUnsignedPayloadMiddleware`: the request body is unseekable, so the SDK cannot compute a payload hash over plain http.
- `RequestChecksumCalculationWhenRequired` (+ response equivalent): SDK-default CRC32 trailer checksums re-introduce aws-chunked encoding, which S3-compatible backends may reject.

`Gateway.SetClientOptions` lets a service contribute `s3.Options` per backend (Retryer, instrumented HTTPClient, timeouts); its options are applied **after** the settings above so the defaults stay unless deliberately overridden. The hook must be set before serving and be deterministic per backend — clients are cached by backend identity and a cached client is reused without consulting it.

## Routing (handler.go)

- A single catch-all route with manual dispatch; `http.ServeMux` patterns are unusable (path cleaning + 301 redirects break S3 keys and signatures).
- Unknown query subresources return 501 loudly (never silently ignore — SDK operations must fail visibly). The `x-id` query param (SDK operation hint) and `x-amz-*` query keys (presigned auth params, hoisted headers) are exempt.
- Each dispatch branch checks the allowed `paramSet` and calls `authorize` with the mapped `s3:*` action.
- **Hooks (intercept.go).** After the policies allow an operation, `dispatch` runs it through `Authorizer` and the `Interceptor` chain, so a service can refuse what policies cannot express (quota, suspension, rate limit) and meter what it served. `Op` carries method, action, identity, front bucket and key, plus `BytesIn`/`BytesOut`, which are wire byte counts filled in by the time `next` returns — an aws-chunked upload therefore counts its framing. The counting wrappers are installed by `wrapHandler`; a handler invoked outside it counts nothing rather than failing. The hooks run once per inbound request, around the handler, so retries the backend SDK makes inside `next` are invisible to them and nothing is counted twice; a client that retries arrives as a separate request and is hooked again, which is simply another request the gateway served. DeleteObjects authorizes per object; copies authorize `s3:GetObject` on the source and `s3:PutObject` on the destination. `Op.BucketMetadata`/`Op.KeyMetadata` pass `store.Bucket.Metadata`/`store.Key.Metadata` through untouched so hooks reuse what the store's lookups already loaded instead of querying again; the gateway never interprets them and they are `json:"-"` on purpose — `Op` is emitted as-is by observers, and whether that data belongs in a log is the service's call, not the gateway's.

## Testing

- stdlib `testing` + `google/go-cmp` only; no testify. External test packages (`s3gw_test`, `s3rp_test`, ...) with `export_test.go` for internals. Table tests, `t.Context()`.
- **Gateway tests live in `s3gw`, not the root package.** They were moved there because s3gw is meant to become its own repository: its own tests covered 28.9% of it while the root package's brought that to 67.3%, so a split would have shipped it undertested. The root package now tests only root code — config validation, the config store's contract, and the integration suite. Do not add a gateway test to the root package because a fixture happens to be easier there.
- The main e2e pattern (`s3gw/sdkclient_test.go`): `httptest.NewServer(gw.Handler())` with a **real aws-sdk-go-v2 client** using front credentials (genuine client-side SigV4) and a `stubBackend` injected via `SetBackend` (which pre-warms the backend client cache). This covers verification → routing → response mapping without any real backend. Tests needing more than one tenant, user or bucket build a `memStore` from the compact specs in `s3gw/storefixture_test.go`, which parse bucket policies and apply `Backend.SetDefaults` exactly as a real Store must.
- Integration tests are env-gated: `S3RP_TEST_BACKEND_ENDPOINT` (+ optional key env vars). Backends in compose.yml:
  - versitygw (default, fast): `docker compose up -d --wait versitygw`, endpoint `http://localhost:7070`. The `--versioning-dir` flag must precede the positional data dir (urfave/cli stops parsing flags after positionals).
  - Ceph RGW (`ceph` profile, heavyweight): `docker compose up -d --wait ceph`, endpoint `http://127.0.0.1:7480`. **Use 127.0.0.1, never localhost** — RGW resolves Host names not matching `rgw dns name` as virtual-hosted bucket names. Keep the image on a non-EOL Ceph release (currently Squid; Reef is EOL).
  - **Never use MinIO** — its OSS edition is effectively unmaintained.
- CI runs unit tests (go 1.25/1.26, `-race`) and the integration suite as a backend matrix (versitygw / ceph, `fail-fast: false`).
- Policy evaluation is on the hot path of every request (per object for DeleteObjects), so it is performance-sensitive. `policy/bench_test.go` measures the worst case the caps allow (adversarial patterns, `BenchmarkEvaluate` / `BenchmarkAllows` / `BenchmarkDeleteObjects`). When changing anything under `policy/` or the authorization path (`bucketpolicy.go`, the DeleteObjects loop), **always run `go test ./policy -bench . -benchmem` and confirm no unintended regression** (watch both ns/op and allocs/op — an alloc jump usually means the pattern precompilation or the DeleteObjects de-amplification was defeated).

## Conventions

- Branch per change; never commit directly to main. Run `go fmt ./...` and `go fix ./...` before committing; `git add <file>`, not `-A`. Concise English commit messages and PR descriptions.
- Error responses: S3 XML via `s3err.Error` (`s3err.FromSDKError` preserves the backend's code and status; `wellKnownErrorStatus` maps code-only errors). The backend's **message** is deliberately not preserved: `canonicalMessage` gives each code S3's own wording and an unknown code becomes the code itself, with the backend's wording kept as the cause for the observer. A security review raised forwarding it as a disclosure risk; probing showed the risk is real but narrower than claimed. What was measured: versitygw, Ceph RGW and Amazon S3 all word their messages generically, and where AWS does name a resource it does so in separate XML elements (`BucketName`, `Endpoint`) that the SDK's deserializer drops — so no bundled backend leaks today. What is not guaranteed: AWS documents detailed authorization messages naming the principal and resource for some S3 denials (the principal there is the operator's, not the tenant's), and any backend may word anything into a message. The rule is therefore defense in depth plus uniformity — a message written by another system is not the proxy's to relay — not a fix for a reproduced leak: for one missing key versitygw says "The specified key does not exist." and RGW says "NoSuchKey". Errors the proxy raises itself keep their own message (they pass through `FromSDKError` via `errors.As`). Do not reintroduce a root alias for it — extracted packages are referenced qualified so the dependency is visible. Note `s3err` is the package name, so a local variable holding an error is `s3e`. HEAD and 304 responses must not carry a body. Every response gets `x-amz-request-id`.
- **The gateway does not log; it observes.** `Gateway.SetObserver` is called once per request in `wrapHandler`, after the response is written, with a `RequestInfo`. It is assembled as the request proceeds — `wrapHandler` puts it in the request context, `handleRequest` fills `Tenant`/`User` once the signature verifies and `dispatch` attaches the `Op` once routing and the policies pass — so a request refused before reaching an operation still records who asked. It also carries what the client was told (`Status`, `Code`), the cause (`Err`), the byte counts and the duration, and has JSON tags so it can be emitted as it stands (`MarshalJSON` renders `Err` as its message, since an error marshals to an empty object). Without an observer `s3gw` is silent — the root package installs one (`logRequest` in s3rp.go) that produces the access and failure lines. `RequestInfo.RawQuery` is already redacted: knowing what a presigned signature looks like belongs to the package, not the caller. The only log left inside `s3gw` is the warning when copying a response body fails, where the status has already been sent and no error can be returned.
- **Failures are reported once, at the boundary.** `s3err.Error` carries an unexported `cause` (`s3err.Internal(err, msg)`, `.WithCause(err)`, and `FromSDKError`, which always keeps the SDK error — a transport failure has no API error code, so otherwise the reason vanishes). `wrapHandler` hands it to the observer exactly once, keyed by the same `x-amz-request-id` the client is given, so a reported id leads straight to the reason. Do not log at the failure site, and never render the cause: it is unexported and absent from the XML on purpose, because it may name backend endpoints and buckets. The extracted packages therefore do not import `log/slog` — they return causes and let the caller decide.
- Secrets use `store.Password` (masked on JSON/YAML marshal). The local `s3rp.yml` is an untracked personal config — never commit it.
- Update README.md when adding or changing operations; the supported-operations list and the Limitations section must stay accurate.
